# 任务日志 / 错误档 模板与字段（全局唯一事实源）

> 从项目内 `docs/superpowers/journal/README.md` 提升为全局——新项目不必先有那个文件。
> 建档时把需要的部分复制过去即可。

本目录承载**任务日志**与**项目错误档**。硬规则写在全局 `~/.claude/CLAUDE.md` §6，
本文件只放**模板与字段说明**——按需读取，不占常驻上下文。

- `YYYY-MM-DD-<slug>.md` —— 任务日志，一任务一份
- `MISTAKES.md` —— 项目错误档
- `verify-band-rules.sh` —— 行数复核与错误档筛选的验收脚本（可直接跑）

## 1. 任务日志模板

```markdown
# 任务日志：<任务名>
状态：进行中 | 已交付 | 已搁置
最后更新：YYYY-MM-DD

## 📍 当前状态（每次更新覆写此节 —— 断片后先读这里）
- 进行到：<阶段 X / 第 N 步>
- 下一步：<具体到可直接开工的一句话>
- 未决问题：<等用户裁定的 / 悬而未决的>
- 关键路径文件：<path:line>
- 已定裁决（仍生效的约束，一行一条）：
  - <结论> —— <一句理由>

## 📜 事件流（只追加，绝不改写历史）
- [MM-DD HH:MM] <事件> —— <证据指针>     # 同日多事件时 HH:MM 便于定位；
                                          # 单日少量事件可简写 [MM-DD]
```

### 快照五字段说明

| 字段 | 写什么 | 为何需要 |
|---|---|---|
| `进行到` | 当前阶段 / 第几步 | 断片后的定位锚 |
| `下一步` | 具体到可直接开工的一句话 | 恢复后不必重新决策 |
| `未决问题` | 等用户裁定的、悬而未决的 | 防止未决事项被遗忘 |
| `关键路径文件` | `path:line` | 省去重新查找 |
| `已定裁决` | 仍生效的约束，结论 + 一句理由 | **仅记阶段与下一步无法恢复"为什么这么定"** |

### 必记事件（其余不记；派活/交付结果、L2/L3 各拆两条，故表内 9 行）

| 事件 | 记什么 |
|---|---|
| 用户裁定 | 结论 + 关键理由 |
| Plan-Gate 收口 | 过 / 打回、致命项处置 |
| **实证流入口判定** | **入口判据四条的逐条结论 + 决策表**（`ops/empirical-flow.md` §1）。**必须写在任何 Gate 前实现派活之前**（含 ① 测量代码与 ③ 候选原型）——这是两类窄例外能否成立的前提之一，**事后补记不算数** |
| 派活 | 派给谁、任务、预估行数 |
| 交付结果 | 实际行数、测试结果；**若 >400 行须附超出原因**（`[DELEGATION-BAND]` 要求）—— **与派活分两条追加，不回写历史** |
| L2 审查 | `must-fix` / `nit` 各几条、采纳或判误报及理由 |
| L3 审查 | 第几轮、按该次审查自身的严重度分级计数、采纳或判误报及理由 |
| 阻塞与未决 | 卡在哪、等谁 |
| 交付/合并 | PR 号、SHA、测试实据 |

涉及子代理产出或审查意见的事件**须带证据指针**（`.plangate/<run>/…`、PR 号、测试命令），
不能只写结论。

## 2. 错误档条目模板

```markdown
## [E00N] YYYY-MM-DD · <一句话标题>
- **有效性**：active
- **处置**：未修复
- **触发场景**：<什么时候会碰上——扫描入口，只读这行即可判定相关性>
- **错误做法**：<具体做了什么>
- **后果**：<造成了什么，给人判断轻重>
- **正确做法**：<该怎么做，可直接抄进简报>
- **根因**：<为什么会错，防只治标>
```

### 字段说明（条目共 9 个数据字段 + 标题）

| 字段 | 取值 / 写什么 | 用途 |
|---|---|---|
| `[E00N]` 编号 | 顺序编号 | 便于口头指代与交叉引用（**注意：简报里不能只写编号，须逐字抄字段内容**——子代理读不到本文件） |
| 标题 | 一句话概括 | `## [E00N] 日期 · <标题>` 中的标题部分 |
| 日期 | `YYYY-MM-DD` | 记录时间 |
| **`有效性`** | `active` / `superseded-by-E0NN` / `obsolete` | **决定是否进简报**——只有 `active` 进 |
| **`处置`** | `未修复` / `已规避` / `已修复` | 仅供人判断轻重，**不影响是否进简报** |
| `触发场景` | 什么时候会碰上 | **扫描入口**，派活前只读这列 |
| `错误做法` | 具体做了什么 | 供人对照理解；**不进简报**（简报只抄 `触发场景`+`正确做法`） |
| `后果` | 造成了什么 | 提供"值得警惕"的分量 |
| `正确做法` | 该怎么做 | **进简报的两字段之一**（另一个是 `触发场景`）|
| `根因` | 为什么会错 | 防只治标；判断新错误是否与旧条目同源 |

> **两个状态字段为何正交**：`有效性` 管"这条还算不算数"，`处置` 管"这个坑修没修"。
> **未修复的坑仍是 `active`，照样进简报，而且最该进**——曾误设为单一字段，
> 导致按写入规则填"未修复"的条目永远不满足读取规则"只取 active"，
> 最该预警的错误反而进不了简报。

## 3. 行数复核命令（`[DELEGATION-BAND]` 上界的执行口径）

### git 仓库内

```bash
snap() {  # 用临时 index 生成一棵完整树，不碰真实暂存区
  local i; i=$(mktemp) || return 1; rm -f "$i"
  # 必须先从 HEAD 初始化，否则漏计"被 .gitignore 覆盖但仓库仍在跟踪"的文件
  if git rev-parse --verify -q HEAD >/dev/null; then
    GIT_INDEX_FILE="$i" git read-tree HEAD || return 1
  fi
  GIT_INDEX_FILE="$i" git add -A --force || return 1   # --force 收录 ignored-untracked；失败必须阻断
  GIT_INDEX_FILE="$i" git write-tree || return 1
}
# ⚠️ 两次 snap 之间【必须真的隔着子代理干活】。连着跑必然得零差异——
#    故 BEFORE 要落盘持久化，跨委派存活（会话/进程都可能换）。

# 状态文件位置必须用 --git-path 解析：linked worktree 里 .git 是【文件】不是目录，
# 直写 .git/xxx 会报 "not a directory" —— 而`[DELEGATION-BAND]`恰恰要求在独立 worktree 里干活。
STATE=$(git rev-parse --git-path BAND_BEFORE_TREE)

# ── 派活【前】执行 ──
snap > "$STATE" || { echo "前置快照失败，阻断"; exit 1; }

# ── 子代理干活 ──（此处是委派，不是脚本的一部分）

# ── 交付【后】执行 ──
BEFORE=$(cat "$STATE") || { echo "前置树丢失，阻断"; exit 1; }
git rev-parse --verify -q "$BEFORE^{tree}" >/dev/null \
  || { echo "前置树无效，阻断"; exit 1; }          # 校验后才敢用
AFTER=$(snap) || { echo "后置快照失败，阻断"; exit 1; }
if [ "$BEFORE" = "$AFTER" ]; then
  echo "前后树相同——若子代理确实改过代码，按兜底判据判阻断转人工"
fi
git diff --numstat "$BEFORE" "$AFTER" || { echo "diff 失败，阻断（保留状态文件供重试）"; exit 1; }
rm -f "$STATE"                                   # 仅在成功后清理
```

### 非 git 目录

```bash
ROOT="/abs/path/to/project"            # 必须显式赋值
# 【先规范化再检查】否则 ROOT="/." 或 "$HOME/." 能绕过守卫再塌成 / 或家目录
[ -n "$ROOT" ] && [ -d "$ROOT" ] || { echo "ROOT 未定义/不存在，阻断"; exit 1; }
ROOT=$(cd "$ROOT" && pwd -P) || { echo "ROOT 规范化失败，阻断"; exit 1; }
HOME_P=$(cd "$HOME" && pwd -P) || { echo "HOME 规范化失败，阻断"; exit 1; }
[ "$ROOT" != "/" ] && [ "$ROOT" != "$HOME_P" ] \
  || { echo "ROOT 为根目录/家目录，阻断"; exit 1; }

SNAP=$(mktemp -d) || { echo "mktemp 失败，阻断"; exit 1; }   # 失败立即 fail-closed
SNAP=$(cd "$SNAP" && pwd -P) || { echo "SNAP 规范化失败，阻断"; exit 1; }
case "$SNAP/" in "$ROOT"/*) echo "SNAP 落在 ROOT 内会导致套娃快照，阻断"; exit 1;; esac
# trap 用单引号会在【退出时】才展开 $SNAP——若中途改写 SNAP 会清错路径，故固定当前值
trap "rm -rf '$SNAP'" EXIT             # 用完即清，避免留下整份源码副本

cp -a "$ROOT"/. "$SNAP/before" || { echo "快照失败，阻断"; exit 1; }
# 必须放进 if 捕获：set -e 下 `cmd; rc=$?` 会在赋值前就退出（rc=1 是"有差异"的正常码）
if git diff --no-index --numstat "$SNAP/before" "$ROOT"; then rc=0; else rc=$?; fi
[ $rc -le 1 ] || { echo "diff 异常 rc=$rc，阻断"; exit 1; }   # 只容忍 0/1
```

### 口径定位：尽力估算 + 异常阻断（用户裁定）

**行数是质量的代理指标，不是审计对象。** 追求滴水不漏的精确计数会把工具复杂度推到失控——
下列漏计情形**全部由 Codex 对抗审查提出**，多数已实测坐实（逐项标注），且**每轮复检都还能找出新的**——这正是判据必须兜底而非列举的原因。
故规则定位为：常规场景用上面的命令估算，**遇到算不准的情形一律阻断转人工**。

### 已发现的漏计情形（多类且持续增加；逐项标注实测/推断）

| # | 情形 | 实测后果 | 处置 |
|---|---|---|---|
| 1 | 用 `git diff <前置树>`（工作区比较） | 新建 30 行文件**完全漏计**，纯新增交付算成 0 行 | 改 tree-to-tree（已修） |
| 2 | 临时 index 空起手 | "被 gitignore 覆盖但仍被跟踪"的文件判为已删除，50 行记成 `0 1`（净 **−1**）**倒送额度** | `read-tree HEAD` 起手（已修） |
| 3 | `git add -A` 不加 `--force` | ignored 且 untracked 的新路径下 651 行，前后树哈希**完全相同、彻底隐形** | 加 `--force`（已修） |
| 4 | LFS / `.gitattributes` clean filter | 601 行源码被 filter 压成 **1 行**，漏计 600 | **阻断转人工** |
| 5 | 子模块 / 嵌套 Git 仓 *(推断)* | 父仓只见 gitlink，内部改动不可见 | **阻断转人工 + 各仓汇总后再判档** |
| 6 | clean filter 的**其他来源** *(实测)* | `$GIT_DIR/info/attributes`、`core.attributesFile` 同样生效，601 行压成 1 行 | 阻断转人工 |
| 7 | **符号链接指向计量根之外** *(实测)* | 经 `src/shared -> /external` 改 500 行，**git 与非 git 两套口径同时归零** | 阻断转人工 |

### 阻断判据：兜底式，不是列举式

**判据分两层**：
- **规范覆盖层**：凡机器读到的数字**可能偏离「按本规则应计入的实现代码净新增量」**者，
  一律属本判据管辖——不因清单没列而豁免。
- **可观察触发层**（实操何时阻断）：命中下列已知情形、或反向自检发现量级不符、
  或有其他具体可疑迹象时阻断。**不承诺自动发现完全不可观察的漏计**——
  那是已接受的残余风险（呼应"尽力估算"定位），不是判据失效。

之所以不用列举式清单：漏计路径按"审查一轮出一两个"的节奏持续冒出（已 7 类），
**列举的边界永远追不上"还有一种情形"**。兜底式判据不依赖穷举。

**已知触发情形（提示用，不穷尽；标注实测/推断）**：

| 情形 | 实测后果 |
|---|---|
| `numstat` 出现非数字（二进制 `- -`） | awk 求和静默得 0 |
| 生效的 clean filter（**任何来源**：LFS / `.gitattributes` / `$GIT_DIR/info/attributes` / `core.attributesFile`） | 601 行源码被压成 **1 行** |
| 子模块 / 嵌套 Git 仓 *(git 语义推断，未单独实测)* | 父仓只见 gitlink，内部改动不可见 |
| **符号链接指向计量根之外** | 经 `src/shared -> /external` 改 500 行，**git 与非 git 两套口径同时归零** |
| 出现未声明路径 | 归类失败 |
| 同一文件混有实现与内联测试 | `numstat` 只给整文件数，无法机械唯一归类 |

**反向自检（比任何清单都可靠）**：复核出的数字若与"子代理自述改了什么"量级明显不符，
**以不符为准判阻断**——数字小得可疑时先怀疑漏计，而不是庆幸合规。

**转人工不是放水**：仍要判档、仍要记日志、>600 仍是委派失败。
只是把"算出多少"从机器换成人，避免机器给出一个**自信但错误**的数字。

### 归类规则

先 diff **完整变更集**再归类，每条路径唯一归入「实现 / 测试 / 明确排除」。
**优先级：实现 > 排除，但测试始终豁免**——含实现改动的路径不得单独扣除其中的
格式化 / 生成物部分；测试代码永远按测试计、不进实现额度。
**多处计量（子模块 / 多目录）属同一次委派，汇总后再套 400/600 阈值。**

### 已知残余风险（不修，用户知情）

- `git add` 会把 ignored-untracked 内容写入真实 `.git/objects`（`GIT_INDEX_FILE`
  只隔离暂存区，不隔离对象库），可能产生悬空对象。**含敏感文件（`.env`）的仓库慎用**，
  或改用独立临时仓库计量。
- `snap()` 的临时 index 文件未清理，反复执行会在临时目录留下小文件（非 git 分支的 `$SNAP` 已用 `trap` 清理）。
