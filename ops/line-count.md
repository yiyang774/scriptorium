# 行数复核与计量口径（从 CLAUDE.md `[DELEGATION-BAND]` 外置）

> **两个时点都要读本文件**：① **派活或自己动手【之前】**（基线快照必须在写第一行代码前取，事后补不回来）；② 交付后复核时。命令与口径都是实测定下来的（多类漏计情形已坐实），
> 凭记忆写会静默漏计——最坏是净新增被算成 0 或负数，硬上限直接失效。
> 可执行脚本：**`~/.claude/ops/verify-band-rules.sh`（全局，必定存在）**；项目内若有 `docs/superpowers/journal/README.md` 可一并参考，**但不得依赖它存在**。

## 复核口径与兜底判据

   - **交付后必须机械复核，口径是「尽力估算 + 异常阻断」**（命令见本文件下方与 `~/.claude/ops/verify-band-rules.sh`）。**行数是质量的代理指标，不是审计对象**——追求滴水不漏的精确计数会把工具复杂度推到失控（已发现多类漏计情形且持续增加），故：
     - **常规路径**：用临时 index 在派活前后各生成一棵完整树做 tree-to-tree 比较。三处必须：① **`read-tree HEAD` 起手**（否则"被 gitignore 覆盖但仍被跟踪"的文件会判为已删除、**倒送额度**）；② **`git add -A --force`**（不加会漏掉 **ignored 且 untracked** 的文件——实测在 `.gitignore` 覆盖的新路径下写 651 行，前后树哈希**完全相同、代码彻底隐形**）；③ **`git add` 失败必须阻断**。非 git 目录用 `cp -a` 快照 + `git diff --no-index --numstat`（**只容忍 rc=0/1**）。
     - **异常即阻断转人工**（不猜、不放行）。判据是**兜底式而非列举式**，分两层：
       - **规范覆盖层**：凡机器读到的数字**可能偏离「按本规则应计入的实现代码净新增量」**者，一律属本判据管辖——不因"清单没列"而豁免。
       - **可观察触发层**（实操何时阻断）：命中下列已知情形之一，**或**反向自检发现数字与子代理自述量级明显不符，**或**有其他具体可疑迹象时阻断，由 L0 主循环人工核对后再套三档，绝不按算出的数字放行。**不承诺自动发现完全不可观察的漏计**——那是已接受的残余风险，不是本判据失效。
       已知触发情形（**不穷尽，仅作提示**；标注实测/推断）：`numstat` 出现非数字（二进制 `- -`）；生效的 **clean filter**（LFS、`.gitattributes`、`$GIT_DIR/info/attributes`、`core.attributesFile` 等**任何来源**——实测 601 行被压成 1 行；**子模块 / 嵌套 Git 仓**（父仓只见 gitlink；*git 语义推断，未单独实测*）；**符号链接指向计量根之外**——实测经 `src/shared -> /external` 改 500 行，**git 与非 git 两套口径同时归零**；出现未声明路径。
     - **反向自检（比清单更可靠）**：复核出的数字若与"子代理自述改了什么"量级明显不符，**以不符为准判阻断**——数字小得可疑时，先怀疑漏计而非庆幸合规。
     - **多处计量须汇总后再套阈值**：子模块 / 嵌套仓 / 多目录分别计得的数字**属同一次委派**，相加后判档——不得父仓 350 + 子模块 350 各自判合规。
     - **归类**：先 diff 完整变更集再归类，每条路径唯一归入「实现 / 测试 / 明确排除」。**优先级：实现 > 排除，但测试豁免**——含实现改动的路径不得单独扣除其中的格式化 / 生成物部分；**测试代码不进实现额度**。**注意：此处"测试代码"在计量语境中仅指纯断言与纯数据 fixture**；test helper / fixture 生成器 / runner 脚本按兜底原则**归实现**（见下）。**同一文件混有实现与内联测试时，该文件无法机械唯一归类 → 按上条"异常即阻断转人工"处理**（L0 主循环目测实现段落量级即可，不必逐行）。
     - **不接受子代理自报代替实测**；同一工作区不并发派多个写代码子代理。
   - **【单一定义处】三个口径分开，其余章节只引用不重述**（防口径漂移）：
     - **审查对象（L2 / L3 管什么）**：**一次交付的完整变更集**——含新增、**修改、删除、重构、测试、配置**。**不是"净新增"**：净新增为 0 的纯改写、纯删除同样要审。L3 另覆盖跨文件与内容层面（依 `CLAUDE.md §3 [ENGINE-ASSIGNMENT]`）。
     - **计量对象（行数三档管什么）**：只计**实现代码的净新增**（口径见本条上文）。这是**阈值的计量口径，不是审查范围**——两者不可混用。
     - **术语**：下文"**L0 主循环直接实现**"= L0 主循环依本条下界例外自己上手写代码（与"L1 委派"相对）。
     - **计量单位**（阈值按什么汇总）：**一个可追溯的交付变更集**——从"动手前的快照"到"提交 L2 审查"之间的全部相关路径与仓库，**汇总计一次**；边界以**可独立验收的计划单元**为准。**禁止按文件 / commit / 会话 / 作者拆分来规避阈值**。
   - **L0 主循环自己上手写的代码，受同等约束**（堵"自己动手就绕过全部审查"的后门）：L0 主循环依下界例外直接上手时，同样要**交付后机械复核行数**、同样要**发起 L2 跨家族快审**、同样受三档判定与 L3 约束。
     **审查者家族按【当次 L0 实际所属家族】跨出**（不预设 L0 是谁）：L0=Claude 家族 → L2 用 Codex `gpt-5.6-luna`（`bin/l2 --author claude`）；
     L0=Codex 家族 → L2 用 Claude(Sonnet/Haiku)（`bin/l2 --author codex`）。
     **L0 属 Claude / Codex 之外的家族时**：`bin/l2` 当前只支持这两族，故按**从严**处置——
     用 `--author mixed` 发起（两族各审一轮，对该 L0 必然都是异家族），并在日志写明所取解释。
     - **基线时点**：动手写第一个字之前取快照（git 用 `snap()`，非 git 用 `cp -a`）；到提交 L2 时结算。中途分几次改、改几个文件、跨几个仓，**一律汇总**。
     - **超 600 的处置**：**先重新核验下界例外是否仍成立——通常应转派 L1**（注意：**转派前必须先把它重新规划成各自可独立验收且 ≤600 行的单元**，L1 同受 600 硬上限；若原单元根本无法合法拆分，则**保持阻断**，不是换个作者重做同一超限单元）；只有"委派确实不可行"时才允许 L0 主循环自己拆成 ≤600 的单元逐个重做（含重新过 L2）。超限产出**整目录归档**（`cp -a` 或 `tar`，**不用 git patch**——它保不住 untracked / 二进制 / 文件模式 / symlink 目标），归档后校验可完整恢复再回到基线；**校验不过就阻断，不许硬删**。
     - **must-fix 修完要再发起一轮 L2**（修复本身也是新变更；复审须拿到**最终完整变更集作上下文**，但责任范围是修复 diff；L2 失败则按 `~/.claude/ops/l2.md` §3 的 fail-不阻断语义记录后进 L3）。
   - **【兜底原则】判不准就从严 + 留痕**（替代逐条穷举边界组合，同「异常即阻断」的思路）：凡计量单位、作者家族、实现/测试归类**出现歧义或多种解释**，**一律取最严的那种解释**，并在任务日志写明取了哪种、为何。已知歧义及其配套边界处置：
     - **L1 委派与 L0 主循环直接实现混在同一批交付**（如 L1 写 350 行、L0 主循环又写 350 行后一起提交）→ 从严即**按交付集汇总判档**（700 行 → 超 600，走硬上限处置），**不按作者各自计**。禁止靠"换个人写"洗额度。
     - **混合作者的 L2 选档** → 从严即**两个家族各审一轮完整变更集**（Codex 审一遍、Claude 审一遍）。这样"审查方须跨出产出者家族"对每一部分都至少被满足一次，且无人为拆分导致的交互盲区；成本换彻底，与 L2 全量策略一致。
     - **测试与实现双用途文件**（测试 helper / fixture 生成器 / test runner 脚本）→ **归类从严：按实现计**（它们含可执行逻辑、能改变产物）；**只有纯断言与纯数据 fixture 才享测试豁免**。豁免是给"测试本身"的，不是给"标签叫 test 的可执行逻辑"的。
     - **基线没能及时取全**（如中途才发现另一个相关仓库）→ 从严即**不得结算、不得提交 L2**，须回到能取全基线的状态重做。
     - **交付集的边界** → 以**可独立验收的计划单元**为界；**"提交 L2"这个动作本身不创建新单位**，不得每写 400 行就提交一次来重置计量。
   - **纯文档交付不触发 L2**（规范、说明、注释类改动）；但**代码交付附带的文档随完整变更集一并进 L2**（审查者需要它作上下文）。判定仍依下条的执行链标准。
   - **什么算"实现代码"：以是否进入执行链为准，不看扩展名、不采信自述**：凡内容会被**运行时 / 构建 / 部署 / 测试 / 安全自动化**读取，并能改变**命令、控制流、数据转换、权限或产物**者，一律按实现代码处理——hook 脚本、CI 的 `run:`、package scripts、权限矩阵、路由表、feature flag、依赖版本皆属此列。**纯说明性文档与示例可豁免；但若 Markdown / 模板 / 注释里的内容会被脚本抽取、生成或复制进运行产物，则计入。** 代码文件里只改注释可不计行数，**但同一变更只要含行为修改，就不得以"主要是注释"为由豁免审查**。
